# Windows 录制重构性能对比

2026-10-31 在 AMD Radeon 8060S / AMDh264Encoder 上测量。基线提交为 `0398b0ac45fb72d035248ce7f935d578db7087b2`，当前版本取未提交工作树的原生录制源码。两版在同一个隔离 Rust 程序中使用相同依赖和 Release 优化编译，每个样本启动独立进程；不修改用户安装或蓝图。

采集矩形为物理像素 (100,100,897,360)，60 fps、H.264 硬件编码、20 Mbps、光标开启。每次就绪后录制 4 秒，按旧单路、新单路、共享双写入、双编码顺序执行三轮。双编码的第二路为 640×360；其余为 898×360（偶数补齐）。媒体资源创建和停止耗时计入 CPU 及总墙钟时间。

CPU 为进程内核加用户时间除以墙钟时间，100% 表示占满一个逻辑核；内存为整个原生进程的峰值工作集，不是 GPU 显存，不包含 WebView。表格给出三次测量的中位数。

| 拓扑 | CPU 单核占比 | 峰值工作集 MiB | 初始化 ms | 停止 ms | 每个输出帧数 |
| --- | ---: | ---: | ---: | ---: | --- |
| 重构前单路 | 15.6% | 85.4 | 458 | 32 | 240–241 |
| 当前单路 | 13.3% | 95.9 | 436 | 31 | 240–241 |
| 一个编码器、两个写入端 | 14.3% | 95.9 | 434 | 36 | 240–241 |
| 两个编码器、各一个写入端 | 20.4% | 111.4 | 618 | 38 | 240 |

18 个输出文件全部用 Media Foundation 解码验证，尺寸和帧数正确，所有样本的 droppedFrames 均为 0。共享编码双写入比当前单路增加约 1.0 个百分点的单核 CPU，占用工作集近似相同；双编码增加约 7.1 个百分点和 15.4 MiB。当前单路比基线峰值工作集增加约 10.6 MiB。

旧版 CPU 范围 9.4%–17.6%，当前单路 11.5%–14.3%，范围明显重叠。当前单路中位数较低不足以证明稳定加速：样本短、桌面内容和系统负载未锁定、顺序固定。该结果仅证明这台设备在此尺寸的四种拓扑持续输出正常，不能代表 4K、高运动画面、GPU 显存或硬件编码并发上限。更大压力下须重新测量。

## 重现与证据

`npm run test:recording-performance` 默认使用以上基线，可在命令尾传入其他基线提交。要求 Windows、SDR 显示器、硬件 H.264 编码器和本地 Rust 依赖缓存。测试建立隔离目录、编译、实录三轮并解码所有输出；不纳入普通单元测试。

原始证据：`apps/desktop/src-tauri/target/performance-1793440297182/`，包含基线／当前源码快照、Cargo.lock、results.json、summary.json、decoded.json 和 18 个视频。基准程序为 `apps/desktop/scripts/fixtures/recording-performance.rs`，编排脚本为 `apps/desktop/scripts/verify-recording-performance.mjs`。

最终命令端到端重跑也通过（`performance-1793440474155`）：另 18 个视频全部解码，12 个样本零丢帧。旧单路／当前单路／共享双写入／双编码的 CPU 中位数分别为 17.6%／14.6%／15.3%／20.7%，工作集中位数为 85.5／95.9／96.1／111.5 MiB。两轮表现方向一致但存在测量波动，仍按上述短时测试边界解释。
