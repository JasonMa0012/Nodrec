# Media Output：编码与写入

## 当前实现

Hardware Auto 会依次尝试捕获适配器上的硬件编码器，完成格式设置与启动后才视为可用；失败时释放激活对象并继续候选项。统一日志记录编码配置、捕获适配器、候选编码器数量与 CLSID、异步／D3D11 能力，以及各初始化调用前的步骤。调用失败保留原 HRESULT，并附带编码器名称和失败步骤（设备管理器、CBR、码率、GOP、B 帧、输入／输出类型、流启动）。Writer 失败与最终输出统计也写入同一日志。另一台 Windows 设备的 0x80004005 原因仍待新版错误及设备复测确认。

- 原生重构性能已做同机对比，旧／新单路、共享双写入和双编码各三轮，18 个输出均可解码，统计零丢帧。当前单路峰值工作集增加约 10.6 MiB；CPU 样本波动重叠，不能据短时中位数声称稳定加速。方法、CPU／内存／耗时结果和重现入口见 [性能报告](../recording-performance.md)。下方旧批次中的“性能基线尚未完成”已被本批替代；GPU 显存和并发容量上限仍未测量。

- `npm run test:recording-faults` 在真实 WGC／硬件编码运行中注入写入失败（共享编码和独立编码）、慢写入导致两秒包队列满、编码分支失败及全部输出失败。2026-10-31 五个场景通过：健康分支在故障后继续编码并发布，失败端仅留 partial，全部失败自动停止。九份健康／部分 MP4 均经 Media Foundation 解码成功。产物 src-tauri/target/live-recording-faults-1793437286279。注入仅编译进 cfg(test)，常规单测默认忽略硬件场景，硬件命令显式运行。
- 硬件编码激活对象由生命周期守卫持有，正常退出及初始化失败均调用 ShutdownObject，遵循 [Microsoft 的释放约定](https://learn.microsoft.com/en-us/windows/win32/api/mfobjects/nf-mfobjects-imfactivate-shutdownobject)。连续硬件测试在测试线程维持 COM apartment；未初始化该 apartment 的无界面测试曾在第二次 WGC 支持查询超时，不将其误报为桌面故障。此注入不模拟物理设备拔出或驱动重置，性能基线对比仍未完成。

- 新增 `npm run test:output-isolation`：Release 实机共享编码双写入、双编码双写入的发布冲突验证；录制启动后占用第二个最终路径，断言旧文件不覆盖、失败端 partial 保留、健康端发布成功，并解码健康及部分文件。2026-10-31 两种拓扑均通过，898×360 和 640×360 动态画面均有 120 次以上变化，停止耗时 34／35 ms。产物 src-tauri/target/output-isolation-1793436785638/result.json。此场景验证收尾发布隔离，未覆盖录制中磁盘故障、队列超限或 GPU 设备丢失。
- 故障实测修复汇总错误错误指向健康输出 partial 的问题：仅报告实际存在的部分文件；失败收尾也保留 stopMs。Rust 47 项测试及上述实机回归通过。

- 失败编码分支在当前调度轮末移出活动数组，立即释放编码和 GPU 转换资源；仅保留写入线程句柄与结果供最终收尾。原生入口统一检查分支采集配置一致，输出最终路径和 partial 路径共同预留，拒绝相对路径／大小写别名及最终名与临时名冲突。单测通过；设备故障下的释放尚未实机注入验证。

- 2026-10-30 debug 双编码回归（含 2 秒暂停）：AMD 8060S，898×360 与 640×360 均解码 181 帧，时间戳 0..30000000（100 ns），文件约 3 秒，停止 34 ms；两路 finished=true、error=null。大图 sceneChanges=3，小图为 0，不能据此认定两路动态图像验收完成。产物 src-tauri/target/bypass-regression-20261030-174017。此测试未覆盖 Release WebView 或编码故障。

## 迁移记录（按实现批次，早期限制可能已被后续批次替代）

- 编码分支初始化错误按分支保存到输出统计，至少一个成功则继续；运行期 tick 错误关闭该编码器的全部下游发送器，其他分支继续，全部失败才停止采集。失败分支不发布完整文件，健康分支独立排空及发布。原生单测覆盖错误标记和关闭发送器；GPU 初始化／运行故障的实机注入尚未验证，失败编码资源目前保留到会话收尾释放。

- 原生 launch_graph 已接入多个编码分支，图启动按编码节点 ID 分组，一次 WGC 更新供全部分支采样；各分支独立转换／编码／写入和排空。2026-10-30 debug 实机双 AMDh264Encoder 输出 898×360 与 640×360，各解码 61 帧，时间戳均 0..10000000（100 ns），停止 35 ms。产物 src-tauri/target/two-encoders-20261030-172742。运行期编码失败尚会结束整个采集循环，编码器初始化失败隔离和 Release WebView 验收仍未完成。

- 单个编码分支现由 EncoderBranch 持有编码器、GPU 转换、配置、输出广播及独立采样进度；tick 接收会话时间与采集更新数，分别推进输出、跳帧及重复帧统计。当前调度仍只有一个分支实例，多分支数组与错误隔离尚待接入；本次重构后真实录制待复验。

- GPU 转换资源可复用同一 D3D11 device/context 和采集裁剪纹理，分支独立创建处理器、NV12 分配器及 MF manager；检查输入尺寸一致。当前单编码路径已改走共享设备分支构造，源构造仍包含待拆除的临时转换初始化；多编码调度未接入。2026-10-30 debug smoke 双文件约 1 秒成功，逐输出 finished=true、error=null，停止 33 ms；copy.mp4 解码验证见本轮工具结果，产物 src-tauri/target/shared-device-20261030-165936。

- 单写入端初始化错误现记录并关闭该端，至少一个端成功则继续采集，全部失败才拒绝启动。RecordingStats.outputs 返回各输出的最终／部分路径、完成标记和错误，运行循环及收尾更新。已通过原生单测，尚未做初始化故障实机注入；UI 输出详情展示仍待接入。

- 2026-10-30 原生 debug recording-smoke 实机验证单编码双写入：AMD Radeon 8060S／AMDh264Encoder，898×360、60 fps，约 2 秒，main.mp4 与 copy.mp4 各解码 120 帧，时间戳 0..19833333（100 ns），各检测 3 次画面变化，停止 32 ms。产物位于 src-tauri/target/multi-output-20261030-165454。仅验证原生双文件通路，未验证 Release WebView、多编码器、长时性能或故障注入。

- 单编码多写入已接入原生启动：图编译输出路径列表交给 launch_outputs，逐端创建 MP4 线程，共享编码包广播并逐端收尾／不覆盖发布；失败端保留部分文件，健康端可发布。启动期任一写入端失败仍中止启动，逐输出统计尚未补齐；多编码实例仍明确拒绝，真实多文件录制尚未验收。

- 编码输出已改用 PacketOutputs 广播容器：每写入端独立 try_send，队列满／断开后关闭该端发送器，其他端继续；全部端失败才向编码循环返回错误。测试覆盖慢端隔离、健康端继续及全失败。当前启动层仍只创建一个实际写入端，结束结果仍聚合失败；多端文件发布和逐输出状态尚待接入。

- 编码包载荷已改为 Arc<[u8]>，入队包装独立持有每写入端额度；PacketWriter::send 负责非阻塞投递及失败归还。单包在复制前限制 64 MiB，队列额度在入队时申请；编码器不再操作写入端额度细节。测试覆盖共享载荷、独立计数及队列满后额度释放。多端广播及调度仍待接入。

- MP4 写入器已改为接收独立输出路径和 EncodedVideoFormat（codec、尺寸、帧率、码率、配置头），不再接收完整 RecordingPlan；封装入口拒绝不支持的 Codec 和无效尺寸／帧率。当前格式由单编码调用端构造，多编码／多写入调度尚未实现，真实录制仍待重验。

- 原生 MP4 写入队列现同时限制包数量和 64 MiB 在途编码包内存；申请内存额度后才复制编码包，队列拒收、写入完成或异常释放包时自动归还额度。编码输出原本已使用非阻塞 try_send，本次保留该错误路径。新增额度上限、溢出和释放测试；当前仍为单写入端，分支隔离尚未实现。

- 编码节点类型现为 `encode_media_foundation`，节点配置及蓝图参数使用 `codec`（当前只支持 H.264）；模板、图编辑器、后端解析和测试已同步，不保留旧 encode 节点／encoder 配置字段兼容。运行统计中的 encoder 仍表示实际选中的 MFT 名称。32 项 Rust 测试、57 项模型测试及前端构建通过，尚未重新完成真实录制验收。

编码节点目录及默认模板显示为 Media Foundation Encode，H.264 字段显示为 Codec；目前仍使用旧版文件模型与单输出运行层。V2、独立 Control Editor、多路执行和其他 Provider 尚未实现。

Windows Media Foundation 已实现实时无声 H.264→MP4，入口为 `recording.rs`／`recording/windows.rs`：

- Hardware Auto 使用 `MFTEnum2` 按捕获适配器 LUID 枚举并激活硬件编码器，记录实际名称和适配器；要求 D3D11 输入，不隐式回退软件或跨适配器 CPU 拷贝。
- Software 显式使用系统 H.264 编码器，复用 GPU 转换，仅在编码入口回读 NV12；会增加 CPU 负担。
- CBR 0.1–200 Mbps（默认 20）、High Profile、2 秒 GOP、无 B 帧；24／30／60／120 fps，Source Size／1080p／1440p。设备实际不接受的配置在启动时报错。
- 压缩包复制到有界队列（最多目标帧率的 2 秒），由独立原生线程持续写 MP4。写入跟不上时明确失败；不丢弃已经编码的包。GPU 转换后显式 Flush，避免异步编码器读取旧黑纹理。
- 停止先关闭捕获并排空编码器，再等待 Sink Writer Finalize 和文件句柄释放；成功后用不覆盖目标的同目录 MoveFileEx 发布最终 MP4。录制中使用 `.partial.mp4`，失败保留并返回路径。编码器排空上限 10 秒；底层驱动／磁盘阻塞不承诺硬性停止期限。

## 验收

本机 `AMDh264Encoder` 与 `Microsoft H.264 (Software)` 均已生成可完整解码的 898×360 MP4，软件路径已测暂停／继续；AMD 1440p60 短录通过。Release 端到端区域录制停止约 7–8 ms，并验证已有最终文件不被覆盖；首帧已目视检查。长录制结果和性能边界统一记录在 [验收场景](../testing.md)。音轨、NVIDIA／Intel 和游戏负载未验证。
