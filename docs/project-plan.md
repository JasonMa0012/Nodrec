# 项目总体规划

## 已明确的需求

Nodrec 将录屏、操作记录、节点工作流与验证连接起来。普通用户用简单预设，高级用户编辑节点，Agent 通过 MCP 使用产品能力。第一阶段覆盖 Windows 桌面应用与 UE／游戏开发测试。

| ID | 一期需求 | 模块 | 验收 |
| --- | --- | --- | --- |
| R01 | 全屏／区域／指定应用窗口录屏，可显示鼠标 | Capture | T02 |
| R02 | 常用分辨率／帧率／编码选项，结束自动保存到指定目录 | Capture、Media Output、Storage | T02、T03 |
| R03 | 音频输入节点与视频输出配合 | Audio | T03 |
| R04 | 录屏同时记录键鼠与快捷键 | Input、Runtime | T04 |
| R05 | 鼠标绝对／语义模式，语义记录 UI 树和事件相对位置 | Input | T05 |
| R06 | 回放模拟对应输入，同时录屏 | Replay | T06 |
| R07 | 回放完成后生成相对基线的像素差异统计 | Verification | T07 |
| R08 | 两个直观预设，编辑预设使用节点编辑器 | Desktop、Workflow | T08 |
| R09 | 捕获、音频、编码、写入、字符串／唯一路径节点；参数可连线 | Workflow、Media Output | T01、T03 |

范围调整：一期先做键鼠，手柄录制与回放后续考虑。系统样式与各平台原生 UI 不再作为无条件约束；其他平台是明确的后续目标，优先降低未来重复开发成本。项目文档中文正文、英文标识。当前桌面应用使用 React + Tauri 和 React Flow，已有 Windows 原生无声录屏；具体实现及尚未验证的范围见 [模块文档](index.md#模块文档)。

## 建议开发顺序（待确认）

先验证关键技术和方案，再逐步形成简单录屏、键鼠回放、差异报告、节点创作与完整 MCP 闭环。尽早用一个真实工作流同时从 UI／MCP 驱动，验证高级编辑能力与简单预设能否共用设计。函数、子图和事件仍属于一期，但具体交付拆分再讨论。

已确认的蓝图格式、首版录屏管线和 Windows 发布方式见 [技术决策](decisions.md)；尚未选择的细节不在此预定。

## 需要主动质疑与澄清的问题

- **节点化范围**：录屏软件加通用可编程平台会显著扩大一期；Houdini 数据流与蓝图事件并非天然兼容。先定义必要的工作流能力，避免把可编程性本身变成主要产品。
- **语义记录**：游戏／自绘控件不一定有可用 UI 树；树也不是事件发生瞬间的稳定快照。需要讨论缺失时的行为、记录粒度、隐私与成本。
- **回放可重复性**：同样输入不代表同样结果；初始状态、焦点、DPI、键盘布局、鼠标加速与目标应用延迟都可能改变行为。
- **验证可信度**：有损编码、光标、动画、随机渲染和时间错位会造成像素差异。应区分执行问题与画面统计；如何对齐、保存什么基线还未选择。
- **MCP 对等范围**：“任何 UI 操作”是否包括视口／选择等纯编辑状态、OS 对话框和无 UI 启动，需要明确；不能只提供启动停止就声称完整对等。
- **UI 与跨平台**：系统样式不保证最低成本；通用 UI 也不能消除捕获、输入和权限的平台差异。多平台时间表会影响当前选型。
- **采集边界与容量**：“所有输入”可能包含敏感键入；录制包、UI 树及无损帧的容量需要真实数据评估。全局采集范围和音频类型待确认。

## 后续方向

手柄、其他平台、更多编码器／容器、HDR、多显示器组合、更可靠的等待／检查点及 Agent 分析。扩展按实际需求再确认，不自动成为一期承诺。
