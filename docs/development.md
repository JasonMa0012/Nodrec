# 开发与知识库维护规则

默认不提交、不推送、不安装系统驱动、不改用户资产或清理工作目录。仅在任务明确要求时执行这些操作。
修改代码后必须自行编译并验证；已有进程阻塞构建或验证时，应自行关闭该阻塞进程后重试。
优先复用项目已有或成熟的 UI 组件，不为常见交互自绘控件；确需自建时说明现有组件无法满足需求的原因。

## 修改代码必须同步文档

代码与受影响文档在同一任务中更新：行为和实现状态写模块文档，跨模块接口写接口文档，已确认方案写技术决策。只维护相关事实，避免重复描述；不影响文档事实的等价修改可说明无需更新的原因。

## 模块文档固定结构

1. **当前实现**：真实状态、代码入口、验证证据与已知限制；无代码写未实现。
2. **职责与边界**：模块负责什么、与谁协作。
3. **一期目标**：待实现能力与尚未确定的问题。
4. **验收**：验证场景和实际结果。
5. **未来规划**：一期以外的方向。

实现后将相关计划移入当前实现，不复制源码或维护第二份实现清单。

## 证据、决策与交接

- 区分需求、候选方案、已确认决策与已验证事实；规则随实践逐步形成，不提前把猜测写成永久约束。
- 技术决策只在用户比较方案、选择并明确确认后记录；写明选择、理由、代价与未验证部分。AI 推荐或 API 文档不等同于用户确认或运行证据。
- 对用户提出的所有需求保持审视：主动分析长期成本、隐藏前提、细节风险及更简单的替代方案，说明取舍；不能因为需求来自用户就默认它合理，也不能未经确认删减需求。
- 验证结论写清方法、结果与限制；编译、单测和真实运行分别报告。任务交接说明代码／文档变化及未完成事项。
